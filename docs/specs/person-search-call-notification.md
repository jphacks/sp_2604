# 人物検索結果の着信通知 仕様

人物検索の結果を「電話がかかってきた」形で知らせる機能の仕様。ステータス: **実装済み (実機での動作は未確認)**

## 目的

人物検索の結果を、着信に応答して耳元で聞けるようにする。相手の前でもスマートフォンを耳に当てるだけで、相手の名前をこっそり確認できる。

## 方式

- CallKit の `CXProvider.reportNewIncomingCall` をアプリからローカルで呼び、着信画面を出す。
- サーバー、VoIP プッシュ (PushKit)、外部サービスは使わない。
- 読み上げは `AVSpeechSynthesizer` を使い、オンデバイスで行う。

### 前提と制約

- 着信を出せるのは、アプリのプロセスが動いている間だけ (前面に表示中、またはバックグラウンドで解析中)。
- バックグラウンドでの解析は `BGContinuedProcessingTask` で続けている (開始できない場合は `UIApplication.beginBackgroundTask` で 30 秒程度延長するだけ)。ユーザーや OS に打ち切られてアプリがサスペンドされると、着信は出せない。
- 今のバックグラウンド実行は、解析が完了した直後に終わる (`ConversationAnalysisService.stream`)。着信 → 応答待ち → 読み上げの間もアプリが動き続けられるよう、着信処理の間はバックグラウンド実行を別に延長する。着信中・通話中にアプリが生かされ続けるかは、実機で確認する。
- CallKit の着信 UI はシミュレーターでは動かない。動作確認は実機で行う。

## 発火タイミング

人物検索が完了したとき。`ProcessingViewModel.search()` の `.completed` で、今 `NotifyPersonSearchResultUseCase` を呼んでいる箇所から呼ぶ。

- 録音中は鳴らさない。CallKit がオーディオセッションを取ると、`AudioRecorderClient` の中断処理で録音が止まるため。人物検索の完了時は録音が終わっているので衝突しない。

## 鳴らす条件と読み上げ内容

人物検索の結果が出たら、候補の有無にかかわらず着信を鳴らし、結果ごとに読み上げる内容を変える。検索がエラーで終わった場合 (`PersonSearchError.selfNotIdentified` / `.partnerNotDetected` など) は着信を鳴らさない。

| 結果 | 条件 | 読み上げ内容 (例) |
| --- | --- | --- |
| 候補あり | 候補が 1 件以上 | 「この方は、〇〇さんではありませんか？△△所属です。前回は、□□で、次のような話をしました。(要約)」 |
| 該当者なし | 候補が 0 件 | 「該当する人が見つかりませんでした。」 |

- 候補ありのときは **1 位の候補 1 人だけ** を読む。
- 読み上げる項目は **名前・所属・前回会った場所・前回の話の要約 (`Encounter.summary`)** の 4 つだけにする。
  - 所属が空文字なら、その文は読まない。
  - 要約が空、または出会い記録がなければ、「前回は…」以降を読まない。会った場所 (`Encounter.place`) が未設定なら、「前回は、次のような話をしました。」と場所を省いて読む。
- 名前は、まず漢字のまま読ませる。実機で聞いて読み間違いが気になる場合は、`Profile` に読み仮名 (`nameReading`) を追加する。DB マイグレーションと登録画面の変更が必要になるため、別タスクとする。

## 着信の見た目

| 項目 | 仕様 |
| --- | --- |
| 発信者名 | 「Dareda」(汎用名)。候補の名前は表示しない。相手に画面を見られても分からないようにするため |
| 着信音 | 通常どおり鳴らす (システムの着信音)。マナーモード時は端末の設定に従う |
| 電話アプリの履歴 | 残さない (`includesCallsInRecents = false`) |
| 音声の出力先 | 通常の通話と同じく、受話口のスピーカー |

## 通話の流れ

1. 人物検索が完了したら、着信を出す。
2. ユーザーが応答したら、`provider(_:didActivate:)` で読み上げを始める。
3. 読み上げが終わったら、自動で通話を切る。
4. 一定時間 (25 秒) 応答がなければ、自動で着信をやめる。着信中の実行時間の延長 (約 30 秒) に収めるため。
5. 通話後に画面は移動しない。結果は、今の処理画面にこれまでどおり表示される。

## ローカル通知との関係

着信を基本とし、着信で伝えられなかったときだけ既存のローカル通知 (`NotifyPersonSearchResultUseCase`) で知らせる。

| 状況 | 動作 |
| --- | --- |
| 着信に応答した | ローカル通知は出さない |
| 着信を出せなかった (`reportNewIncomingCall` が失敗した) | ローカル通知を出す |
| 拒否した・応答しなかった | ローカル通知を出す |
| アプリがサスペンドされていて、検索完了の処理自体が走らなかった | どちらも出ない (アプリに戻ると処理が再開される) |

- 既存のローカル通知は、今は候補ありのときだけ出している。該当者なしのときも通知するかは、未決事項とする。
- 既存のローカル通知は、アプリ表示中は抑止される。着信の代わりに出す場合も、この挙動は変えない。

## 設定

- 設定画面で、着信通知のオン・オフを切り替えられるようにする。初期値はオン。
- **初期実装には含めず、後回しにする。** 初期実装では常にオンとして動かす。
- オフのときは、これまでどおりローカル通知だけを使う。

## 未決事項

- **該当者なしになるのは、保存済みのプロフィールが 0 件のときだけ。** 今の `SearchPersonUseCase` は類似度の閾値を持たず、常に上位の候補を返す。そのため、まったくの別人でも 1 位の候補として名前を読み上げる。閾値を設けるか、「おそらく〇〇さんです」のように言い方を変えるかを決める。
- 該当者なしのときに、ローカル通知の代替を出すかどうか (上記)。

## 想定する実装範囲

アーキテクチャガイド (`AGENTS.md`) のレイヤ構成に従う。

| レイヤ | 追加・変更するもの |
| --- | --- |

| その他 | `main.swift` (全シナリオでテストダブルに差し替える)、UI テスト |

### 設計上の注意

- **通知の UseCase は 1 つにまとめる。** UseCase から別の UseCase は呼べないため、着信用の UseCase を新しく作ると、ローカル通知への切り替えが書けない。既存の `NotifyPersonSearchResultUseCase` の中で `VoiceCallGateway` と `UserNotificationGateway` を順に使う。
- **ViewModel は通知の完了を待たない。** 今は `.completed` で通知を `await` してから画面の状態を更新している。着信は応答待ちと読み上げで数十秒かかるため、別の `Task` で呼び、結果の表示を先に行う。
- **CallKitClient は状態を持つ。** `CXProvider` とそのデリゲート、通話中の UUID、応答待ちの continuation を保持する必要がある。`BackgroundTaskClient` と同じく、`Impl` を `final class` にして状態を `Mutex` で守る形にする。
- **オーディオセッション。** 受話口から読み上げるため、`provider(_:didActivate:)` で渡されたセッション (`.playAndRecord` / `.voiceChat`) の上で `AVSpeechSynthesizer` を鳴らす。録音用のセッション設定と衝突しないよう、録音中は鳴らさない方針を守る。

- Info.plist の `UIBackgroundModes` に `voip` を追加する (PushKit は使わないが、CallKit で着信を報告するために必要)。
- 変更不要なもの: Entitlements、サーバー・Terraform
